# ロボ箱庭すごろく — C2C（Client-to-Client）版 / Elixir 分散ノード

[robo-sugoroku](https://github.com/keith-river/robo-sugoroku)（Node.js + Express + Socket.io の**中央ゲームサーバ**構成）を、
**中央サーバなし**・**各PCがElixirの分散ノードとして対等に動く**構成に作り変えたものです。
ゲームのルール・3D画面（three.js）はそのまま。外部ライブラリなし（OTP標準のみ）、LANだけで動きます。

Elixir,OTPによるC2C版、開発者の設計思想、要求仕様、開発コンテクストを共有して、Anthropic Claudeがコード生成、
テスト検証しました。 

| | 元（中央集権） | この版（C2C） |
|---|---|---|
| ゲームの正 | サーバの `game.js` が1つ | **全ピアが同じエンジンの複製**を持つ（`Robo.Engine`） |
| サイコロ・初期配置 | サーバが `Math.random()` | **全員が出した乱数から決まる**（commit-reveal） |
| ジャンケンの手の秘匿 | サーバが預かる | **ハッシュで先に約束**し、全員揃ってから開示 |
| CPU・時間切れ | サーバのタイマー | **担当ノード**のアクタ（`Robo.Peer`）が実行 |
| 切断 | サーバが検知してCPU化 | **次のノード**が検知してCPUとして引き継ぐ |
| 単一障害点 | サーバ | **なし**（どのPCが落ちても残りで続行） |
| 通信 | ブラウザ⇔サーバ(Socket.io) | ブラウザ⇔自PCのノード(WebSocket)、ノード⇔ノード(分散Erlang) |

## アーキテクチャ

```
  PC-A                         PC-B                         PC-C
┌───────────────────┐       ┌───────────────────┐       ┌───────────────────┐
│ ブラウザ(3D画面)    │       │ ブラウザ(3D画面)    │       │ ブラウザ(3D画面)    │
│   ▲ WebSocket     │       │   ▲ WebSocket     │       │   ▲ WebSocket     │
│ ┌─▼───────────┐   │       │ ┌─▼───────────┐   │       │ ┌─▼───────────┐   │
│ │ Peer (アクタ)│◀──┼───────┼─▶ Peer        │◀──┼───────┼─▶ Peer        │   │
│ │  Engine複製  │  │ 全ピアへ│ |  Engine複製  │   │ 入力を │ | Engine複製   │   │
│ └─────────────┘   │ブロード │ └─────────────┘   │ブロード│ └─────────────┘   │

        分散Erlang(:pg グループ :robo_peers)で全ピアに入力を配る。全員が同じ状態になる。

```

## 仕組み

### 1. 複製ステートマシン
全ピアが同じ純粋関数 `Engine.apply_input(state, from, input)` に同じ入力を適用するので、同じ状態になります。
入力は `{:dir, …}` `{:commit, …}` `{:reveal, …}` など。ブラウザには各ピアが自分の複製から `update {state, events}` を送ります
（元の `main.js` / `scene.js` は無改造。`public/net.js` が Socket.io 互換の薄いシムです）。

### 2. 中央なしで「公平な乱数」を作る（commit-reveal）
1. 全員が乱数 `r` を決め、`SHA-256(round, id, r, salt)` だけを公開（**commit**）
2. 全員の commit が揃ってから、`r` と `salt` を公開（**reveal**）。commit と一致しなければ無効
3. 結果は全員の `r` をまとめたハッシュから決める → **1人でも正直なら、結果を事前に予測・指定することはできない**
   （ただし、最後に reveal する人は「開示する／無効にする」の1bit分だけ結果を選べます。無効化は全員に ⚠️ として公開されます。bench/engine_bench.exs で実測: 目標の目が出る確率 16.7% → 30.8%）

サイコロ・初期配置・最初の手番がこれで決まります。**ジャンケンの手も同じ仕組み**で、相手の手を見てから出すズルができません。
ブラウザに届く `state` に手は含まれず、出したか(commit済みか)の真偽だけです。

### 3. 合意アルゴリズムなしで複製が食い違わない理由
- **書き込み権限は常に1人**：向き選択は手番の人、ジャンケンはその2人だけ。担当(host)ノード以外からの入力は拒否します。
- commit/reveal は**到着順に依存しない**（集合に足すだけ）。
- Erlangの配送は「同じ送信者から」は順序が保たれ、「別の送信者の間」では入れ替わります。
  先に着いた入力（例：向き選択より先に届いた別ピアのcommit）は**捨てずに保留**し、前提が揃ったら適用します（`Engine.early`）。
  → 送信者ごとの順序だけ保った任意の交互配送でも全複製が一致することを、15,000通りの乱択で確認済み。

### 4. 耐障害性（アクタ/OTPらしい部分）
- ノード停止を `:nodedown` で検知 → **名簿順で次のノード**が、落ちた人（とそのCPU）を **CPUとして引き継ぐ**（`takeover`）。
  持ち主が変わると、前の持ち主が出しかけた commit は破棄され、新しい持ち主が出し直します。
- ブラウザを閉じただけ（ノードは生存）なら、5秒の猶予後に自分でCPUへ（ロビーなら退出）。
- 後から参加したノードは、既存ピアから状態を受け取って追いつきます（ゲーム中なら観戦、ロビーに戻ると参加）。
- `Robo.Peer` が落ちても、監督木が再起動し、他ピアから状態を取り直します。ブラウザ接続も自動で付け直されます（強制終了して確認済み）。

## 起動

Elixir 1.12+（OTP 24+）。外部ライブラリは不要です。ビルド：`mix compile`

```bash
# 全PC共通：分散Erlangが使うポート範囲を固定（Firewall用）
export ERL_AFLAGS="-kernel inet_dist_listen_min 9100 inet_dist_listen_max 9105"

# 1台目（192.168.1.10）
ROBO_NAME=たろう elixir --name robo@192.168.1.10 --cookie robo-secret -S mix run --no-halt

# 2台目以降は、すでにいるピアを ROBO_JOIN に指定（誰か1台でよい）
ROBO_JOIN=robo@192.168.1.10 ROBO_NAME=はなこ elixir --name robo@192.168.1.11 --cookie robo-secret -S mix run --no-halt
```
起動すると表示されるURL（例 `http://192.168.1.10:3000/`）を**自分のPC**のブラウザで開きます。名前はロビーでも変更できます。
Windows(PowerShell)は `$env:ROBO_JOIN="…"; $env:ERL_AFLAGS="…"` のように環境変数を先に設定してください。

| 環境変数 | 意味 |
|---|---|
| `ROBO_PORT` | ブラウザ向けHTTP/WebSocketポート（既定3000）。**同じPCで複数ノードを動かすときは変える**（`eaddrinuse`になります） |
| `ROBO_JOIN` | すでにいるピアのノード名（カンマ区切りで複数可）。最初の1台は不要 |
| `ROBO_NAME` | 初期の表示名 |
| `ROBO_SPEED` | 演出・待ち時間の倍率（`0.3`で短縮。開発用。**全ノードで揃える**） |

**Firewall（TCP）**：`3000`（`ROBO_PORT`）、`4369`（epmd）、`9100-9105`（分散Erlang）を各PCで許可。
macOSはFirewallがオンなら、`beam.smp` の着信を許可してください。
同じPCで試す場合は `ROBO_PORT=3001 … --name b@127.0.0.1` のようにポートとノード名を変えます。

## 構成

| ファイル | 役割（元リポジトリとの対応） |
|---|---|
| `lib/robo/engine.ex` | 純粋エンジン（`game.js` の移植＋commit-reveal＋保留） |
| `lib/robo/peer.ex` | 各ノードのアクタ（`server.js` の通信・タイマー相当を分散化） |
| `lib/robo/conn.ex` `web.ex` `ws.ex` `json.ex` | HTTP＋WebSocketを `:gen_tcp` で実装（Express/Socket.io の代わり） |
| `priv/public/` | 元の3Dフロント（`main.js` `scene.js` は無改造）＋ `net.js`（Socket.ioシム） |

## テスト
```bash
mix test                          # エンジン26件（ルール、commit-reveal、複製の収束、300回ランダム対戦 ほか）
pip install websockets
python3 scripts/e2e.py all        # 実ノードを複数起動して自動プレイ: solo / mesh / kill
```
`e2e.py` は、(solo) 1ノードで完走、(mesh) 3ノード+CPU+途中参加ノードで**全ノードの最終状態と出来事列が完全一致**、
(kill) 手番の最中にノードを `SIGKILL` しても**生存ピアが引き継いで完走**、を確認します。

## 限界と信頼モデル（正直に）
- **信頼できるLAN専用**。分散Erlangはcookieを知る相手に何でも実行を許します。ノード名・cookieは推測されにくくしてください。
- commit-reveal は「結果の操作」を防ぎますが、**生きているノードが reveal だけ出さない**と進行が止まります（reveal待ちの時間切れは未実装。ノードが落ちた場合は引き継ぎで解決）。
- **ネットワーク分断**（split-brain）は扱いません。分断中は別々に進み、戻っても統合しません。
- 複製の食い違いを検知・修復する仕組み（状態ダイジェストの突き合わせ）は未実装。上記の保留機構により、通常の遅延・入れ替わりでは起きません。
- 同時に2人がゲーム開始を押しても、開始を提案できるのはロビーのリーダー（名簿先頭の人間）だけにして衝突を避けています。
- 複製の「乱数commitの中身(r, salt)」は各ノードのメモリにあります。`Peer` が再起動するとそれを失い、その回の reveal はできなくなります。
